## Real Findings From Implementation (Not Assumed From Documentation)

- `security-framework`'s `passwords::generic_password` getter takes a `PasswordOptions` builder (`PasswordOptions::new_generic_password(service, account)`), not a plain `(service, account)` pair the way `set_generic_password`/`delete_generic_password` do — confirmed directly against `3.7.0`'s docs.rs pages after an initial, incorrect assumption of a symmetric API.
- `SecKeychain` in this crate version exposes no lock-status query method (no `status()`) — confirmed against the crate's own GitHub source, not merely its docs summary. `CredentialStore::list` therefore derives availability by attempting an actual `secret_store.get` per credential and classifying the resulting `OSStatus` (`errSecItemNotFound = -25300` → missing; `errSecInteractionNotAllowed = -25308` / `errSecAuthFailed = -25293` → locked) rather than a single shared "is the keychain locked" check, a design correction made during implementation, not assumed upfront.
- `osascript -e 'display dialog ... with hidden answer'` hangs indefinitely in this sandboxed environment (no WindowServer/Aqua session) — reproduced directly, killed manually after 8 seconds, confirmed no orphaned process afterward. This drove the independent Rust-side timeout in `OsascriptSecretPrompt` (AppleScript's own `giving up after` clause showed no sign of ever engaging on its own here).
- `security-framework` is already resolved transitively through Tauri's own macOS stack (`tao`/`tauri-runtime-wry`) — confirmed by building `lattice-desktop` after adding it as a direct `lattice-core` dependency, which pulled in no additional packages beyond what adding it to `lattice-core` alone already required.
