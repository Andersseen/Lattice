## Real llmster CLI Evidence

Checked directly against the installed llmster build (CLI commit `71bd99c`, same installation ADR 0010/0011 checked) on the development machine:

- `lms ls --help`, `lms ps --help`, `lms load --help`, `lms unload --help` were run directly; all four commands' flags match `openspec/changes/local-models/design.md`'s "Documentation sources" section exactly, including the absence of any `--json`/output-format flag on `load`/`unload`.
- `lms ls --json` on this machine (LM Studio.app not running headlessly) prints `Waking up LM Studio service...` and does not return within an 8–10 second manual bound, the same daemon-wake gap 0.6 recorded for `lms daemon up --json`. Re-attempted 2026-09-12 after `open -a "LM Studio"`: the GUI process does not stay running in this environment (confirmed via `ps aux` immediately after launch), so the one-time first-run registration this machine needs cannot be completed here either. `ps aux` after every attempt shows no orphaned `lms`/LM Studio process — the no-orphan guarantee holds under this genuine real-world CLI/environment limitation, not only under disposable fixtures.
- Because of the above, no real `lms ls --json`/`lms ps --json` sample was captured to pin the exact JSON field names `ModelDescriptor`/`LoadedModelObservation` deserialize. The parser (`crates/lattice-core/src/model_runtime/models.rs`) is deliberately tolerant — `#[serde(default)]` on every non-identity field plus `#[serde(alias = ...)]` hedges on the most plausible alternate key spellings from the CLI's documented human-readable columns — so an unexpected real shape fails closed to an empty inventory or `Unknown`/`Failed` outcome rather than panicking or reporting a false positive, per ADR 0011.
- One real installed model was found on this machine (`~/.lmstudio/models/lmstudio-community/Qwen2.5-Coder-14B-Instruct-MLX-4bit`), but it is a 14B model, not a small candidate profile, and could not be exercised because of the same daemon-wake gap above.
